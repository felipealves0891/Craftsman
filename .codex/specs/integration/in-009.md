# Plano IN-009: Implementar Rastreio Loggi

## Resumo

Implementar a integracao Loggi como uma nova implementacao de `IShippingTracker`, mantendo o Shipping Context desacoplado das APIs externas. O primeiro escopo sera somente rastreio ativo por API, com desenho preparado para webhook de rastreio, sem cotacao, criacao completa de envio, etiquetas, cancelamento ou alteracoes no modelo interno de `Shipment`.

A integracao deve consultar o rastreio Loggi por `tracking_code`, mapear o status externo para `ShipmentStatus` e retornar `TrackedShipmentStatus` pelo contrato existente. Eventos externos negativos nao devem encerrar automaticamente o envio interno como `Cancelled`; devem ser tratados como ocorrencias externas ate existir um fluxo operacional explicito para decisao de cancelamento/devolucao/perda.

## Passo a Passo

1. Atualizar `.codex/tasks/integration/tasks.md` com uma nova tarefa de implementacao baseada na IN-009, com criterios de aceitacao claros.
2. Criar configuracao `LoggiOptions` com `Enabled`, `Environment`, `BaseUrl`, `ClientId`, `ClientSecret`, `CompanyId`, `TrackingPathTemplate`, `RequestTimeoutSeconds` e `TokenRefreshSkewMinutes`; validar no startup via Options Pattern.
3. Implementar servico de token OAuth V2 usando `POST /v2/oauth2/token`, `client_id` e `client_secret`, com cache em memoria ate proximo da expiracao.
4. Implementar cliente HTTP Loggi com `IHttpClientFactory`, `System.Text.Json`, timeouts configuraveis, logs sem segredos e tratamento explicito de erros.
5. Implementar consulta de rastreio por `GET /v1/companies/{company_id}/packages/{tracking_code}/tracking`, usando Bearer token e retornando o evento/status mais recente disponivel.
6. Implementar mapper de status Loggi para `ShipmentStatus`:
    - `1` Adicionado e `28` Coleta pendente -> `Created`.
    - `3`, `4`, `11`, `13`, `14`, `15`, `16`, `17`, `24`, `25`, `30` -> `InTransit`.
    - `12`, `18`, `10`, `20`, `21`, `22` -> `DeliveryAttempted`.
    - `5` Entregue -> `Delivered`.
    - `2`, `6`, `7`, `8`, `9`, `19`, `23`, `26`, `27`, `29` -> nao converter automaticamente para `Cancelled`; retornar uma ocorrencia rastreavel como `DeliveryAttempted` quando o contrato exigir status interno, ou falhar de forma controlada se a resposta nao tiver um status operacional claro.
7. Implementar `LoggiShippingTracker : IShippingTracker`, normalizando `trackingCode`, chamando o cliente Loggi e retornando `TrackedShipmentStatus`.
8. Desenhar endpoint de webhook como evolucao tecnica do mesmo modulo, com Basic Authentication, HTTPS obrigatorio e processamento idempotente por evento externo; nao persistir historico nesta etapa se o modelo interno nao for expandido.
9. Registrar a integracao no DI apenas quando `Loggi:Enabled = true`. Quando Loggi e Correios estiverem desabilitados, preservar `StaticShippingTracker`.
10. Manter cotacao, criacao assincrona de envio, etiquetas, Loggi Pontos e cancelamento fora desta implementacao.
11. Rodar `dotnet build Craftsman.slnx` e `dotnet test Craftsman.slnx` com `DOTNET_CLI_HOME=D:\Source\Repos\Dotnet\Craftsman\.dotnet-home\.dotnet`.
12. Apos concluir a implementacao e os testes, marcar a nova tarefa de implementacao como concluida em `.codex/tasks/integration/tasks.md`.

## Interfaces e Tipos

- Nao alterar `Shipment`, `ShipmentStatus`, `TrackedShipmentStatus` ou `IShippingTracker`.
- Adicionar tipos de infraestrutura para Loggi: options, DTOs de request/response, token service, tracking client, status mapper, exception/error kind e `LoggiShippingTracker`.
- `LoggiOptions` deve ficar desabilitado por padrao em `appsettings.json` e `appsettings.Development.json`.
- Credenciais (`ClientId`, `ClientSecret`) e `CompanyId` devem vir de configuracao segura por ambiente; nao devem aparecer em logs.
- `TrackingPathTemplate` deve conter `{companyId}` e `{trackingCode}` para permitir ajustes de endpoint sem recompilar.

Mapeamento minimo para o modelo atual:

- `trackingCode` -> `Shipment.TrackingCode`.
- status Loggi atual -> `TrackedShipmentStatus.Status`.
- `status.updatedTime` ou timestamp equivalente do evento -> `TrackedShipmentStatus.TrackedAt`.

Dados fora do modelo atual e recomendados para evolucao futura:

- `loggiKey`;
- historico completo de eventos;
- localidade do evento;
- data prometida;
- acao requerida;
- dados de pacote;
- cotacao;
- etiqueta;
- criacao/cancelamento de envio;
- auditoria de webhook.

## Testes

- Unitarios para `LoggiTrackingStatusMapper`, cobrindo status de criado, transito, tentativa/pendencia, entregue e eventos negativos que nao devem virar `Cancelled`.
- Unitarios para `LoggiTokenService`, cobrindo obtencao de token OAuth V2, cache ate proximo da expiracao e renovacao antes da chamada de rastreio.
- Teste de erro de token classificando `401` como autenticacao e `403` como autorizacao/configuracao.
- Teste de `LoggiTrackingClient` com `HttpMessageHandler` fake, garantindo Bearer token, montagem do endpoint com `company_id` e `tracking_code`, parse do evento mais recente e uso de timeout configurado.
- Testes de erro HTTP classificando `429` como rate limit/transiente, `503` como indisponibilidade transiente e JSON invalido como resposta invalida.
- Teste de `LoggiShippingTracker` retornando `TrackedShipmentStatus` com codigo normalizado, status interno e data rastreada.
- Teste de DI garantindo que `LoggiShippingTracker` so substitui o tracker padrao quando `Loggi:Enabled = true`.
- Build e suite completa da solucao.

## Criterios de Aceitacao

- O dominio de envio nao conhece DTOs, endpoints ou regras especificas da Loggi.
- O primeiro escopo cobre apenas rastreio por API, com webhook documentado como evolucao do mesmo desenho.
- Eventos relevantes da Loggi sao convertidos para `Created`, `InTransit`, `DeliveryAttempted` ou `Delivered`.
- Eventos externos negativos nao cancelam automaticamente o envio interno.
- Credenciais Loggi, `company_id`, `integration_code`, contato com vendas/Sales Engineering e disponibilidade regional ficam documentados ou configuraveis sem hardcode.
- Falhas de autenticacao, autorizacao, rate limit, indisponibilidade e resposta invalida sao tratadas explicitamente.
- Cotacao, criacao de envio, etiqueta, Loggi Pontos e cancelamento permanecem fora do escopo inicial.

## Assumptions

- A primeira implementacao real deve usar `IShippingTracker` para preservar o desacoplamento do Shipping Context.
- `company_id` ja deve estar disponivel para a aplicacao quando `Loggi:Enabled = true`; o fluxo `POST /v1/integrator/activate` com `integration_code` fica documentado, mas nao precisa ser automatizado no primeiro rastreio.
- Webhook exige endpoint HTTPS configurado com a Loggi e Basic Authentication; sem historico de eventos no modelo atual, ele deve apenas alimentar o mesmo mapeamento operacional ou ficar como evolucao posterior.
- Criacao de envio, cotacao e etiqueta exigem dados de endereco, pacote, contrato/homologacao comercial e decisoes operacionais que ainda nao existem no modelo atual.
